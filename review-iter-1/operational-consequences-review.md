## Findings

### OC-1 — ops-doc-reality — **must fix**
- **Location:** `fprime-zephyr/Fs/FatFilenameAllocator/docs/sdd.md:10-11` (also `sdd.md:54-56`, `default/zephyr-config/FatFilenameAllocatorCfg.hpp:9`)
- **Confidence:** high
- **Description:** The SDD says calls on open handles (`f_read`, `f_write`, `f_lseek`, ...) do not use the LFN buffer and that a slot is held only during a "path-taking" call. With exFAT enabled (the configuration the PR targets and sizes for), `f_sync()` on a modified file runs `INIT_NAMEBUFF(fs)` / `FREE_NAMEBUFF()` (ff.c:4248-4270), and `f_close()` calls `f_sync()` first (ff.c:4312). So `Os::File::flush()`/`close()` (Zephyr `fs_sync`/`fs_close`) also take a slot. Consequence when the pool is exhausted at close time: `f_close` returns `FR_NOT_ENOUGH_CORE` before it updates the directory entry. Zephyr `fatfs_close` frees the `FIL` anyway and returns `-ENOMEM` (fat_fs.c:154-163). `fs_close` leaves `zfp->mp` set (fs.c:232-236). `ZephyrFile::close()` discards the return code (`Os/File.cpp:85-86`). The exFAT directory entry (size, first cluster) is never written, so the data written since the last successful sync is unreachable, and no F Prime event reports it. Anyone who sizes the slot count from this SDD text misses this demand.
- **Suggested fix:** Correct the SDD and the config comment. For example, `sdd.md:10-11`:
  ```suggestion
  `f_mkdir`, `f_opendir`, `f_readdir`, ...). With exFAT enabled, `f_sync` and `f_close` on a modified file also use it to rewrite
  the file's directory entry. The buffer is released before the call returns. `f_read`, `f_write` and `f_lseek` do not use it.
  ```
  Add to the Slot count section a WARNING that an exhausted pool at `f_close`/`f_sync` on exFAT loses the directory-entry update, and that `ZephyrFile::close()` does not report it.

### OC-2 — ops-config-extreme — **suggestion**
- **Location:** `fprime-zephyr/Fs/FatFilenameAllocator/docs/sdd.md:54-58`; `default/zephyr-config/FatFilenameAllocatorCfg.hpp:9-11`
- **Confidence:** high
- **Description:** With `CONFIG_FS_FATFS_REENTRANT=y` (the SDD's required configuration), every slot allocation and release in FatFs happens while the per-volume mutex is held (`lock_volume`, ff.c:899-921; `INIT_NAMEBUFF` after `mount_volume`/`validate`, `FREE_NAMEBUFF` before `LEAVE_FF`; `FF_FS_TIMEOUT = K_FOREVER`). Peak `inUse` is therefore `min(threads, FF_VOLUMES)`. The SDD's guidance ("number of threads that may be inside such a call") is safe but wastes memory: on a single-volume deployment that has N file-using threads, it reserves N × 1120 B where 1120 B is enough. At the default of 4, 3360 B of .bss is never usable. The other extreme, `FPRIME_ZEPHYR_FAT_FILENAME_SLOTS < FF_VOLUMES` (e.g. 1 slot, with SD and flash disk both mounted), is legal and nothing checks it. Two threads on different volumes then race. The loser gets `-ENOMEM`, which reaches F Prime as `Os::File::OTHER_ERROR` (`Os/File.cpp:78-80`) on open, or as silent data loss on close (OC-1).
- **Suggested fix:** Documentation plus configuration guidance; a code change is optional. State in the SDD and the config comment: "With CONFIG_FS_FATFS_REENTRANT=y at most one slot per mounted FAT volume is in use; set the count to FF_VOLUMES (or fewer only if fewer threads ever use FatFs). Without REENTRANT, use the number of threads." Optionally default the count to `FF_VOLUMES` when `FF_FS_REENTRANT` is set.

### OC-3 — ops-timing-resource — **suggestion** (operational judgment call)
- **Location:** `fprime-zephyr/Fs/FatFilenameAllocator/docs/sdd.md:91-93`
- **Confidence:** medium
- **Description:** Operational judgment call. Rejecting `dir_clear()` requests is approved decision (2). This finding is only the unquantified worst case. With the pool installed, every `dir_clear()` falls back to `csize` single-sector `disk_write` calls from the window (ff.c:1702-1705), instead of `ceil(csize·SS / 32 KiB)` multi-sector writes. For a 32 KiB cluster that is 64 writes instead of 1. For a 128 KiB exFAT cluster (typical SDXC format) it is 256 writes instead of 4. `dir_clear` runs in `f_mkdir`, and on directory growth inside `f_open(FA_CREATE_*)`, `f_rename` and `f_mkdir` each time a directory crosses a cluster boundary. It runs with the volume mutex held (`K_FOREVER`), so every other thread's FatFs call on that volume (FileDownlink reads, ComLogger/DpWriter writes, PrmDb) blocks for the whole 64–256-write burst. FatFs's own comment says "many single-sector writes may take a time". The SDD describes this only as "slower but correct".
- **Suggested fix:** Add an SDD WARNING (documentation remedy, since the behaviour is approved):
  ```suggestion
  - `dir_clear()` (from `f_mkdir` and directory growth) asks for a cluster-sized buffer and halves the size until it reaches one
    sector. These requests are rejected (counted in `rejectedCount`), and FatFs then clears the cluster one sector at a time from the
    volume window. **WARNING:** that is `csize` single-sector writes per cleared cluster (64 for 32 KiB clusters, 256 for 128 KiB),
    with the volume mutex held. Every other FatFs call on that volume blocks for the whole burst. Pre-create directories, or
    budget this latency for file-creating components.
  ```
